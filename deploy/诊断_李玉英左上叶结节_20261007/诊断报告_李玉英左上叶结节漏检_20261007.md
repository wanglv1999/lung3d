## 三、缺陷 1：NIfTI 的 z 方向符号错误（已铁证）

### 3.1 证据

逐像素比对（转换时面内是 2 取 1，所以 NIfTI 每层应与某张 DICOM 的 `[1::2,1::2]` 完全一致）：

| NIfTI 层 k | 与 inst = k+1 最大像素差 | 与 inst = 454−k 最大像素差 |
|---|---|---|
| 0 | **0** | 4045 |
| 20 | **0** | 4076 |
| 100 | **0** | 4086 |
| 200 | **0** | 4236 |
| 300 | **0** | 4308 |
| 453 | **0** | 4045 |

**11/11 全部逐像素相同，最大差 0** → `NIfTI 层 k ≡ DICOM InstanceNumber k+1`。

### 3.2 矛盾所在

- DICOM 事实：InstanceNumber **1 = 最上层**（IPP z 最大），InstanceNumber 增大 → 变**靠下**。
- 写出的 NIfTI affine：

```
[ -0.3786   0        0       176.33  ]
[  0       -0.3786   0       334.67  ]
[  0        0       +0.7000 -1174.118]   ← z 方向 +0.7
```

affine 声称 **索引增大 → z 增大 → 更靠上（头侧）**，与真实层序**方向相反**。

`SimpleITK` 直接验证：`origin z = -1174.118`（= inst 1 的位置），`direction = [1,0,0, 0,1,0, 0,0,1]`，`TransformIndexToPhysicalPoint((0,0,453))` 给出 z = −857.0，而该层真实 z = −1491.218。**自相矛盾 → 体数据在 S/I 方向被镜像。**

> x、y 两轴方向正确（左肺仍在患者左侧），**只有 z 轴符号错误**，所以是一个纯上下镜像。

### 3.3 后果一：检测器拿到的是"倒过来"的肺

实测 MONAI 预处理链：

```
LoadImage(reader="itkreader") 的 meta affine 与 nibabel 完全一致（z = +0.7）
Orientation(axcodes="RAS") 后 axcodes = ('R','A','S')，affine z 仍为 +0.7  ← 不翻转 z
```

即：`Orientation` 信任了这个错误的 affine，认为自己已经是 RAS，于是**不会把 z 翻回来**；送进 LUNA16 模型的是一副上下镜像的胸腔。模型是在正常 RAS 数据上训练的，镜像输入属于分布外样本。

### 3.4 后果二：导出的 3D 模型上下颠倒

`export_mesh()` 里顶点坐标 = 体素索引经 affine 旋转 + 平移（再 RAS→LPS 翻 x、y）：

```python
R = affine[:3,:3] / np.linalg.norm(affine[:3,:3], axis=0)
A = flipxy @ R @ np.diag(spacing)
world = verts @ A.T + flipxy @ origin
```

z 符号错了，导出网格随之镜像。**解剖判据**（真实解剖中气管顶端应高于肺动脉顶端，因为气管向上延伸到颈部）：

| 结构 | 体素 k 范围 | 模型坐标 z | 真实解剖 z |
|---|---|---|---|
| 气管/气道 | 18–378 | −1161.5 … **−909.5** | −1438.7 … **−1186.7** |
| 肺动脉 | 58–431 | −1133.5 … **−872.4** | −1475.8 … **−1214.7** |
| 肺静脉 | 59–403 | −1132.8 … −892.0 | −1456.2 … −1215.4 |
| 肺结节 | 106–342 | −1099.9 … −934.7 | −1413.5 … −1248.3 |

模型坐标里气管顶端（−909.5）**反而低于**肺动脉顶端（−872.4）——与解剖相反 → **模型整体上下颠倒**（见 `model_orientation.png`）。

由此，模型上的位置与 CT 层面号的关系变成 `inst_模型 = 455 − inst_CT`：真正在 inst 113（左肺上叶）的病灶，在模型里落在与 inst 342（左肺下叶）对应的位置上。

## 四、缺陷 2：缺滑窗推理 → 显存 OOM → CPU 降级

### 4.1 官方设计 vs 本地实现

官方 bundle `monai_nodule/configs/inference.json`：

```json
"detector_ops": [ ...,
  "$@detector.set_sliding_window_inferer(roi_size=@infer_patch_size,
      overlap=0.25, sw_batch_size=1, mode='constant', device='cpu')"
],
"infer_patch_size": [512, 512, 192],
"force_sliding_window": false
```

`monai_nodule/scripts/detection_inferer.py` 中：

```python
use_inferer = (self.force_sliding_window or self.sliding_window_size is not None
               and not all([data_i[0,...].numel() < self.sliding_window_size for data_i in inputs]))
```

本例重采样后 552×552×254 = **77.4 M** 体素 > 512×512×192 = **50.3 M** → 官方流程**必然启用滑窗**。

而 `lung3d_reconstruct.py` 的 `NoduleDetector`：

- `__init__` **从未调用** `set_sliding_window_inferer`；
- `predict()` 里 `self.detector([batch_img[0]])`，`use_inferer` 默认 **False**（见 `retinanet_detector.py:466`）。

→ **整卷 77 M 体素一次性过网**。

### 4.2 实测后果

本机（RTX 5060 Laptop，**8 GB 显存**）实测抛错：

```
torch.AcceleratorError: CUDA error: out of memory
  .../monai/apps/detection/networks/retinanet_detector.py:546 in forward
  .../monai/apps/detection/utils/box_selector.py:133 in select_top_score_idx_per_level
```

现有代码捕获该异常后自动降级 CPU 重试——这正是你日志里 **361.1 s / 446.8 s** 的来源（GPU 正常时应是几十秒）。

实测对比（阈值 0.05，同一份数据）：

| 配置 | 用时 | 检出框数 |
|---|---|---|
| A 现状（错误 affine + 无滑窗） | **830.6 s** | 14 |
| B 修正（正确 affine + 官方滑窗） | **273.3 s** | 12 |

关键框分数在两配置间明显漂移：

| 位置 | A score | B score |
|---|---|---|
| 左肺上叶 inst≈112（**本次病灶**） | 0.984 | 0.953 |
| 左肺下叶 inst≈339 | 0.908 | **0.102** |
| 左肺 inst≈298 | 0.993 | 0.992 |

→ 同一份数据两次运行给出的结节集合与分数**并不稳定**，这对临床使用是不可接受的。

## 五、缺陷 3：模型对磨玻璃/混合密度结节天然偏弱

病灶实测（原始 DICOM，inst 102–118，左肺上叶）：

- 范围约 **11–13 mm**，inst 106–116 可见；
- 主体为 **−720 ~ −300 HU 的磨玻璃成分**；
- **> −300 HU 的实性成分每层仅约 100–370 个体素**（对应约 1–2 mm 实性核心）；
- 同层正常肺野均值约 −902 HU。

→ 属于 **混合磨玻璃结节（part-solid GGN）**。

所用模型为 MONAI 官方 "Lung Nodule CT Detection"（LUNA16 训练，`metadata.json` 标注 `mAP_IoU_0.10 0.852`）。LUNA16 参考标准以**实性结节**为主，对纯/淡磨玻璃结节召回率天然偏低；即便检出，分数与尺寸估计也不稳定（A/B 中 6.9 mm ↔ 6.5 mm，0.984 ↔ 0.953）。

## 七、修复建议（按优先级）

### 1）修 z 方向（必修）

最小改动：读完后按 DICOM 的 IPP 校验方向，不自洽就改 affine 的 z 符号（不改动体数据顺序）：

```python
# dicom_to_nifti() 读入后、写盘前插入
import pydicom
ds0 = pydicom.dcmread(str(file_list[0]), stop_before_pixels=True)
dsN = pydicom.dcmread(str(file_list[-1]), stop_before_pixels=True)
z0 = float(ds0.ImagePositionPatient[2])
zN = float(dsN.ImagePositionPatient[2])
dir_z = float(img.GetDirection()[8])          # 当前 ITK 认为的 z 方向
expected = 1.0 if zN > z0 else -1.0           # 索引增大应走的 z 方向
if dir_z * expected < 0:
    d = list(img.GetDirection())
    d[8] = -d[8]                              # 只翻 z 方向
    img.SetDirection(d)
    img.SetOrigin(img.TransformIndexToPhysicalPoint((0, 0, img.GetSize()[2] - 1)))
```

更稳的做法：不要依赖 `SetFileNames` 的传入顺序，先按 `ImagePositionPatient[2]` **升序**排好文件列表再交给 reader，然后回读校验：

```python
import nibabel as nib
chk = nib.load(str(out_nii))
assert nib.aff2axcodes(chk.affine) == ('L', 'P', 'S') or nib.aff2axcodes(chk.affine) == ('R', 'A', 'S')
```

> 注：本次是**层号自上而下编号**（Siemens 该机型/重建参数）才触发；其他病例如果 InstanceNumber 自下而上，就不受影响 —— 这也解释了为什么以前没发现。

### 2）打开滑窗推理（必修）

`NoduleDetector.predict()` 里：

```python
self.detector.set_sliding_window_inferer(
    roi_size=[512, 512, 192], overlap=0.25, sw_batch_size=1,
    mode="constant", device="cpu")     # 与官方 inference.json 一致
...
preds = self.detector([batch_img[0]], use_inferer=True)
```

预期效果：8 GB 显存下不再 OOM、不再走 CPU（实测 830.6 s → 273.3 s），且与官方验证过的推理路径一致。

### 3）磨玻璃召回（建议）

- 阈值分档：score ≥ 0.3 作为结节输出；0.1–0.3 另存为"待复核"列表，不静默丢弃。
- 或补一路 GGO 敏感后处理：在肺野内找 −750 ~ −300 HU 的局部密度增高团块（LoG/多阈值团块搜索），与模型结果并集。本次那个 inst 106–116 的病灶用肉眼在磨玻璃窗下很容易看到，用该方法可稳定捕获。

### 4）加一致性自检（建议）

处理开始时打印：`aff2axcodes`、层序是否单调、首末层的 IPP z、以及"affine 推断的 z 方向 vs DICOM 实际层序"是否一致；任一不自洽就写入日志并警告。这类静默方向错误一旦发生，后面所有结论都不可信。
